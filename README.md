# Construction Modeling Engine (CME)

Live application: [barajas545.github.io/construction-modeling-engine](https://barajas545.github.io/construction-modeling-engine/)

The Construction Modeling Engine (CME) is DCR's independent platform for digitally modeling how deck projects are constructed.

## Mission

CME represents construction intent as structured, serializable project data. It is a construction modeling engine—not a general-purpose drawing application—and is designed to support intelligent construction objects for estimating, planning, validation, and future workflows.

## Current phase

CME is in active construction-object development. **Deck Boundary**, the first production construction object, provides a structured walkable-surface model, validation, editing workflow, project persistence, and a professional modeling workspace. CME-0101 adds the shared modeling-interaction foundation: fluid viewport navigation, direct construction dimensions, intelligent snapping, adaptive grids, and contextual cursor feedback. CME-0102 establishes progressive construction modeling: one authoritative project grows from rapid field capture into detailed construction modeling without redrawing or duplicating geometry.

The large Progressive Model maturity panel is temporarily hidden to reduce inspector noise. Workflow stage and model maturity remain structured project data; they can return later through a smaller actionable indicator tied to takeoff and estimate readiness.

Project surface and Deck area count now live as compact global metrics in the top bar. The right inspector no longer repeats project totals, local area, or down level; local values remain available through the selected Deck Area annotation. The former manual Establish Boundary action has been removed from the top bar so the primary workspace emphasizes modeling and object-specific actions.

The generic Dimension Annotation inspector card has also been removed. Selecting a dimension now relies exclusively on the sticky contextual object panel, which keeps editing and placement actions available without repeating descriptive instructions farther down the inspector.

Drawing Layers and Snap controls now live behind dedicated Visibility and Snap buttons above Details in the left tool rail. Each opens a mutually exclusive lower-left floating panel with a visible connection to its active button, keeping the right inspector focused on selected construction objects while preserving quick tablet access to layer and precision settings.

While drawing a new Deck Boundary, every previously placed corner is an active temporary inference reference. Horizontal, vertical, 22.5°, and 45° guides can combine the current segment direction with an earlier corner—especially the first corner—to place the final corner and close an orthogonal footprint accurately. The current drawing anchor is excluded from its own node inference.

The project name in the top bar now opens a device-local project library. Projects autosave independently and can be renamed, created, opened, or deleted with confirmation; the former single-project save migrates automatically. The primary **Save to Step 1** action produces the versioned DCR Sales Hub field-capture contract (Decking square feet, Railing linear feet, Stair count, and sketch identity), sends it to a trusted Sales Hub launch context when available, and otherwise downloads the same JSON as a portable fallback. **Export options** provides a fitted CME Sketch Plan PDF and an explicit Step 1 JSON download. The connection is documented under `specs/integrations/`.

Projects also sync to the DCR OneDrive account under a fixed `CME/` structure: `Projects/CME-000123 — Name/` holds `project.cme.json`, `Exports/{Plans,Takeoffs,DCR Sales Hub}/`, and `Attachments/{Photos,Audio}/`, beside `Templates/{Materials,Assemblies}/`. Projects take a sequential DCR project number on their first OneDrive save and keep it for life. The device copy stays authoritative and OneDrive follows on a debounce, so a dead spot in the field reports *Offline · saved on this device* instead of losing a sketch; concurrent edits from another device are reported for the estimator to resolve rather than silently overwritten. Storage lives behind an adapter boundary in `src/core/storage/` and is inert until an Entra application ID is configured. See `docs/integrations/OneDrive-Setup.md`.

**Export options → Takeoff** opens an editable material workspace. CME generates preliminary Decking & Trim, stair-covering, and Wild Hog railing purchase lines from established construction objects. Calculated quantities, user overrides, manual materials, and optional unit prices remain serializable with the project. Supplier PDFs omit prices, internal PDFs may include them, and a structured Takeoff JSON snapshot establishes the material-list boundary for future DCR Sales Hub reference projects.

**Framing** now begins as an independent construction layer with Joist, Beam, Post, and Pillar objects. Linear members use the same endpoint, grid, CAT, and node-inference snap system as the rest of CME. A selected Joist or Beam can be repeated at 12, 16, 19.2, or 24 inches on centre; copies choose the useful side of the source member and are clipped to the active Deck Boundary rather than extending into open space. Beam posts and footings are derived live, move with the beam, and may be hidden with the Framing layer. Selected Beam endpoints are independently draggable with live snap, support, and Takeoff recalculation. Beam material defaults to 4×6 PT and offers the existing solid 4×6, 4×8, 4×10, and 4×12 profiles plus (2) and (3) ply 2×6, 2×8, 2×10, and 2×12 built-up profiles. Built-up profiles derive maximum post spacing from the 2025 CRC R507.5(1) 40 psf live-load reference using the Joist Field tributary span; intermediate table columns are interpolated without extrapolation. Solid 4× profiles use the corresponding double-2× row only as a preliminary layout aid and remain explicitly marked **Engineering review**. Beams loaded from both sides use the combined tributary span conservatively and also require review. The estimator may add beam posts, while CME prevents a post count below the current derived minimum.

Framing Takeoff counts only objects represented by the model. It does not infer joists from deck area or add a second hidden “standard” beam. Each drawn Beam is independently divided into purchasable 8, 10, 12, 16, and 20-foot stock, minimizing purchased footage before piece count and cut imbalance; for example, a 20′ 3″ Beam produces one 10′ and one 12′ material line. Built-up Beam quantities count every individual ply, while solid and custom Beam lines retain review status. Offcuts are not silently shared between independent beams. Beam-derived and manually placed coincident posts are deduplicated, post stock uses configurable cut yield, and the same derived support locations drive both the plan graphics and material list. This keeps the first framing quantities auditable while the construction rules continue to be refined locally before any cloud or DCR Portal promotion.

Every modeled post/footing connection adds one **Simpson Strong-Tie ABW Post Base** to preliminary Hardware Takeoff. The exact ABW model and size remain marked for confirmation against the selected post and project conditions.

The Framing toolbar is intentionally limited to Joist, Beam, and **Post / Footing**. Legacy Pillar and Repeat/O.C. controls are no longer offered there; Joist Field spacing belongs in selected-field properties. A manual Post / Footing is one serializable support assembly with a visible footing, editable post size label, Simpson ABW base, and concrete allowance. It may be snapped beneath a Beam or Rim / Flush where the estimator wants an additional field support, including the centre of a long Double Joist span. Existing Pillar objects remain readable for backward compatibility.

**House Attachment and Ledger** are related but separate edge properties. Assigning House Attachment enables a joist-bearing Ledger by default; the estimator may turn Ledger off while preserving the relationship to the house. Active Ledger length generates Simpson Strong-Tie SDWS Timber Screw 5″ at the DCR preliminary rate of 5 screws per linear foot. Takeoff buys 50-piece boxes and rounds both required screws and purchased boxes upward, reporting the remaining pieces as usable spare stock. This is an estimating recipe, not an automatic code approval.

An active Ledger also creates an explicitly labeled lumber line under **Framing**. Its stock follows the dominant Joist Field size in the same Deck Boundary and defaults to 2×6 PT before joists exist. CME plans the measured Ledger into commercial stock lengths while its SDWS screws remain in Hardware. Takeoff offers **Detailed by use** for construction review and editing, or a read-only **Consolidated for purchase** view that combines identical material, treatment, dimensions, stock length, and unit across Ledger, Joist, Blocking, Rim / Flush, and Beam roles. The consolidated list is derived only for purchasing and never removes construction meaning from the project model.

**Rim Joist / Flush Beam** enriches an existing Deck Boundary edge instead of drawing duplicate framing over it. The estimator assigns the relationship explicitly; board direction may provide context but does not silently make a structural decision. A selected edge defaults to a single 2×6 PT member and offers 2×8, 2×10, 2×12, Custom, and Double Joist options. The edge retains its Boundary identity, receives a distinct framing treatment in the plan, and contributes independently optimized commercial stock lengths to Framing Takeoff. Member size remains a preliminary DCR estimating choice rather than an automatic span or code approval.

**Joist Field** uses a tablet-first two-selection workflow. The user first chooses the Deck Boundary to fill, then presses any visible Boundary, Beam, Joist, or CAT line and drags perpendicular to establish layout direction. The reference line controls orientation and O.C. origin only; it does not become a structural support. CME extends the parallel lattice across the complete selected DB, then intersects each joist axis with the actual Ledger, Beam, and Rim / Flush supports to create separate supported bays. This allows a diagonal Rim to carry joists beyond the endpoint of a shorter Ledger. Unsupported intervals remain red in preview and are not established. New field joists default to the preliminary 2×6 PT selection. Takeoff chooses the shortest 8, 10, 12, 16, or 20-foot commercial board that can produce each joist; spans beyond 20 feet are marked REVIEW instead of receiving an unsupported splice.

The selected Deck Boundary remains the authoritative scope and owner of its Joist Field. A Rim / Flush edge is nevertheless treated as one physical structural member: if an edge owned by an adjacent DB crosses or coincides with the selected deck surface, CME clips it to that surface and allows joists from either side to terminate on it. Double Joist configuration is preserved. The relationship never merges the two Deck Boundaries, moves joists into the neighbor, or duplicates Rim / Flush material in Takeoff; Ledgers remain private to their owning DB.

Joist Field now distinguishes a **continuous physical joist run** from its supported bays. Ledger, intermediate beams, and the terminal rim remain bay boundaries for span validation, but they no longer create duplicate cut pieces in the model or Takeoff. The first validation profile follows the 2025 California Residential Code / 2024 IRC R507.6 prescriptive reference for No. 2 wet-service lumber at 40 psf live plus 10 psf dead load, with separate Douglas Fir-Larch and Redwood groups at 12, 16, and 24 inches O.C. A continuous run that exceeds 20-foot commercial stock or contains an over-span bay receives a selectable warning triangle; acknowledgment never deletes the finding. Commercial Takeoff packs compatible short cuts of the same joist material into shared 8, 10, 12, 16, or 20-foot stock and reports the stock actually purchased. Joists also have an independent Visibility sublayer so beams, posts, and footings can remain visible while joist runs are hidden. Local amendments, unusual loading, and manufacturer decking limits still require estimator or engineering review.

A selected field joist now exposes coordinated **Move mesh** and **Single joist** controls. Move mesh shifts the complete field phase in real time, regenerates every regular member against the owning Deck Boundary and current structural supports, and recalculates Takeoff as one undoable edit. Single joist places one additional supported member parallel to the field at the clicked DB location. It remains explicitly marked as a manual parallel member and locked to the field, so later mesh movement preserves its relative position rather than leaving an isolated line behind.

Joist profile and on-centre spacing are **Joist Field properties**, never per-member overrides. Selecting any joist exposes 12″, 16″, 24″, and custom 1″–48″ O.C. controls plus one shared 2×6, 2×8, 2×10, or 2×12 PT profile and lumber span group. Applying either setting regenerates the complete array inside its Deck Boundary, preserves valid manually added parallel joists, recalculates Blocking, Ledger inheritance, span validation, and Takeoff, and remains one Undo operation. The selected physical joist may be deleted independently, or the complete Joist Field and its Blocking settings may be removed together.

Changing the Joist Field profile also synchronizes every active Rim / Flush edge in the same Deck Boundary while preserving whether each edge is a single or double joist. Rim / Flush construction styling belongs to the Joists visibility layer: hiding Joists removes the structural treatment, but the same geometry remains visible and selectable as an ordinary Deck Boundary edge.

**Joist Blocking** is derived from the Joist Field rather than stored as loose linework. CME creates fixed staggered blocking between adjacent joists wherever they cross a Bottom Beam, then adds intermediate rows so no supported bay longer than 8 feet remains without blocking. The user may add, move, or delete a manual blocking row and may explicitly suppress an automatic row with a visible warning. Blocking shares the Joists visibility layer, follows mesh and support edits, and uses the joist nominal material. Framing Takeoff measures the clear cut between joist faces and packs those cuts into 16-foot stock under a distinct Joist Blocking material line.

Blocking material is resolved once per Joist Field from the dominant regular-array material, never independently from each neighboring joist. This prevents a stale or exceptional member from creating a misleading second Takeoff line. Selecting any blocking row exposes a field-wide material selector: Match Joist Field is the default, while 2×6, 2×8, 2×10, or 2×12 PT becomes an explicit override for every blocking row in that field.

The floating canvas toolbar is now dedicated to Undo, Redo, and high-frequency visibility controls. It provides quick toggles for Railing, Framing, CAT construction lines, and Dimensions without activating their modeling tools. Export menus render above selected-object panels so takeoff and PDF actions remain reachable without clearing the current selection.

**CAT CL** provides independent yellow dashed construction references for field layout. CAT Line uses the same professional cursor guide as Boundary: after the first point it reports live length, angle, and snap feedback and accepts exact imperial or metric entries such as `23in`, `6ft`, or `2m` followed by Enter. A selected straight CAT Line can become an editable arc while preserving its endpoints; selected CAT arcs now display the same radius (R), chord-midpoint height (H), and midpoint nodes used by Deck Boundary arcs, in the CAT visual language. Offset shows a live dimension in the workspace and cursor guide; the estimator may type an exact imperial or metric distance before placing it. The most recent distance becomes **Repeat Offset**, so another line needs only a source selection and side selection. Straight offsets whose source lines share a corner are automatically mitered to one shared offset corner. Arc offsets are concentric: the selected side and distance increase or decrease the original radius rather than translating the curve. Measuring Tape reports horizontal, vertical, and point-to-point distance together in a quieter annotation language. Trim works on straight and curved CAT geometry and removes the touched side at the nearest finite crossing. Extend is a deliberate two-selection operation: the estimator selects the source near the endpoint to change, sees **Extend to line intersection** in the lower-left guide, then selects a second CAT Line or arc. Only the source changes. Straight sources follow their infinite line; curved sources continue around their original radius/circumference to the virtual straight-line or circular intersection. Numbered CAT Notes preserve a fixed arrow point while their label moves freely, and selected Note properties store estimator text plus optional voice audio. CAT construction geometry and CAT dimensions have separate visibility layers. Visible CAT Lines participate in Boundary snap with construction geometry taking priority over CAT and CAT taking priority over the grid. Active line and nearby-node inference support 22.5°, 45°, and 90° relationships. A connected closed CAT loop derives an orange 25%-opacity CAT Boundary and a movable CAT area dimension with a repositionable leader arrow. Both Deck and CAT area panels can hide only their selected Boundary while retaining its area annotation, and **Show all boundaries** restores every hidden Boundary. Converting the CAT annotation to a Deck Boundary removes only the source CAT lines, preserves CAT arcs, and creates a normal serialized construction boundary. The structured objects remain serializable without changing authoritative Deck Boundary topology until that explicit conversion.

Deck Area annotations now reinforce CME's progressive-level model. When a Deck Boundary is below the main project datum, its area label adds a compact down-arrow elevation in inches; main-level decks remain visually simpler. The Deck Area object panel can independently reposition or reset the leader arrow so annotations remain legible without losing their owning deck relationship.

Sprint 2 promotes every boundary segment into a typed construction edge with editable geometry and construction properties. **Stairs** use a tablet-first press-and-drag workflow where total rise is primary and CME derives equal risers from 5 to 7.5 inches plus equal treads from 10 to 11 inches. A Stair is now a separate hosted object with its own four-point geometry and a reference to the supporting Deck Boundary edge; creating or editing it never cuts, splits, or reshapes the DB polygon. The Deck–Stair interface remains selectable and can own Fascia, Picture Frame, and future metadata. Plan graphics use the lower edge and deck interface as the first and final riser locations, drawing only the interior lines required to produce the reported tread count. A serializable Dimensions layer lets users hide annotations, drag labels away from construction, and open linked exact editing by double-clicking. Topology-aware vertex editing supports moving, inserting, removing, splitting, and intelligently merging neighboring corners while retaining construction meaning whenever the resulting boundary remains valid.

**Stair Framing Takeoff** derives 2×12 PT framing directly from each staircase instead of requiring separately drawn members. Every stair receives two side stringers, enough internal stringers to keep actual spacing at or below 12 inches O.C., and one measured 2×12 PT top ledger/header at the deck interface. Stringer purchase length follows the true sloped length from total run and total rise and must fit one continuous 8, 10, 12, 16, or 20-foot stock member; an overlength stringer is retained as an explicit engineering review item rather than receiving an implied splice. The selected Stair panel exposes count, internal supports, actual spacing, slope length, stock length, and header stock, while Detailed Takeoff preserves the Stair Stringer and Stair Ledger/Header roles and Consolidated Purchasing may combine identical 2×12 PT stock with other framing lumber.

Stair placement now snaps each opening side geometrically to an adjacent boundary node within six inches while retaining independent stair-owned identities. A lateral stair line can reference a parallel construction edge without inserting junctions or dividing either DB. Completed stairs own a centered, selectable `STAIRS n` annotation, editable rise/riser/tread properties, and lateral-line handles that change width without allowing free stair-node deformation. The host edge controls the stair angle and the stair follows that edge when the deck moves or reorients. **Delete stairs** removes the hosted object without rebuilding deck geometry. Every visible dimension also has an object-attached leader and arrowhead. Labels and arrow tips have independent serializable positions: **Reposition arrow** makes the tip pulse, then one touch or drag anywhere moves it while preserving the dimension's semantic object relationship.

Boundary edges and corners can now be locked as persistent construction constraints. A locked edge protects both its position and length from direct dragging, exact editing, splitting, constraints, and attached stair placement; a locked corner cannot move, merge, delete, or be replaced. Anchor marks appear inside locked edge dimensions and beside locked nodes so constraint state remains visible on the drawing. Independent **Horizontal**, **Vertical**, and **Lock angle** toggles preserve only orientation, allowing the edge to move parallel and change length directly or through connected geometry. Their structured state, persistent button highlights, and H, V, or ⚓∠ dimension marks keep the active relationship visible on tablet and desktop.

Selected orthogonal corners support a tablet-friendly **45° Chamfer** gesture. During the drag, the original corner becomes a temporary virtual node, two dashed construction legs display equal live setbacks, and a separate dimension reports the finished diagonal length. Releasing removes the temporary references and leaves the new diagonal as an ordinary selectable construction edge with its normal dimension.

Projects may now contain multiple independent **Deck Boundaries**. Every polygon owns a selectable local area annotation and a down-level value, while CME reports the project surface as the sum of all Deck Boundary areas for future estimating. Lower decks receive progressively darker shading. **Move deck area** translates the selected polygon as one construction assembly, preserving hosted stairs, railing references, Level Down geometry, and dimension relationships. While placing stairs, CME searches for a valid landing inside a lower Deck Boundary surface rather than targeting one of its edges. On a coincident shared edge, hit testing automatically resolves the higher deck as the Stair host before searching the lower surface. The resulting Stair stores both deck identities, derives exact rise from their level difference, and regenerates while valid. If no construction-valid landing remains, the stair stays visible in red with an explicit review reason and a direct deletion action.

Each Deck Boundary may now own a serializable **Deck Boarding Direction**. From the selected area annotation, the user chooses any straight Boundary, Stair, Level Down, Railing, or CAT line as the directional reference, then may rotate the result 90 degrees or clear it. A curved Deck Boundary edge may instead become the reference for a concentric curved-board pattern: every board seam retains the selected arc centre and is clipped to the true curved DB outline. CME renders either pattern using an explicit 5.5-inch board width and 3/16-inch gap, keeps it below construction objects and dimensions, omits attached Stair footprints, and hides it with the Decking layer. Curved boarding is a visual and quantity-layout aid; fabrication feasibility and heat-bending requirements remain estimator review items. **Delete deck area** is intentionally separate from deleting its area annotation: a two-step confirmation removes the selected polygon and its dependent Stairs, Railings, Level Down objects, and local dimension state as one undoable construction transaction while preserving independent decks.

The adaptive **Construction Grid** is now a persistent Drawing layer beside Decking, Railing, and Dimensions. Hiding the visual grid does not disable grid snapping; visibility and precision remain separate controls so users can work on a clean drawing while retaining field-friendly placement behavior.

Boundary sketching now includes professional **Node Inference**. While placing a segment, CME can combine its active horizontal, vertical, or 45-degree direction with a matching projection from a nearby construction node. One temporary dashed reference, a highlighted source node, the inferred intersection, and a descriptive cursor label make the relationship clear without cluttering the drawing or creating a permanent constraint. Edge, grid, node, and diagonal inference settings are independent and persistent; touch receives a larger target and release tolerance than mouse input.

**Railing** uses a professional snap-to-snap line workflow. A user can begin at a construction edge, corner, or grid point and drag freely across the interior or exterior of the Deck Boundary to another active snap target while equal sections and posts appear in real time. Edge and grid snaps are independently configurable, and the complete Railing model layer can be hidden to expose construction geometry underneath. Runs use a maximum 6-foot clear span between 3.5-inch posts, share visible posts where they meet, and remain structured construction objects rather than sketch lines. Every physical railing post is rendered once and is individually selectable; Takeoff counts only those visible post markers. A shared non-collinear corner defaults to one post, while **Double post corner** explicitly replaces it with two visible posts separated by one post width. CME then regenerates equal spacing along both affected runs, recalculates panel materials, and removes any intermediate post that is no longer needed to maintain the 6-foot maximum clear span. The corner choice is stored by stable railing endpoint identities so moving connected geometry does not silently reset it. Railing length, panels, posts, and type remain in the selected-object panel instead of producing redundant canvas dimensions. This phase produces geometry and serializable quantities only; pricing remains intentionally outside the object.

Single-click selection opens a temporary sticky object-actions panel at the top of the inspector. Railing actions include deletion, Decking visibility, safe panel-count adjustment, and a structured Wild Hog or Trex system assignment ready for future costing. Construction-edge actions include individual dimension visibility, Fascia and Picture Frame intent, and equal division into two or three property-preserving segments. Corners, dimensions, stairs, and stair interfaces expose their most useful safe actions through the same pattern.

Deck Boundary now presents its computed surface area as a centered, selectable Dimension annotation. The annotation can be dragged, hidden independently, or used as the entry point for whole-boundary operations such as aligning near-orthogonal edges to horizontal and vertical construction planes. House Attachment is available directly in the selected-edge quick actions and remains an edge-owned construction relationship. Assigned House Attachment edges use a persistent construction red, including while selected; a neutral highlight communicates selection without replacing their semantic color.

**Level Down** introduces an independent, serializable construction polyline for changes in deck elevation. A run begins and ends on Deck Boundary geometry, may contain intermediate snapped points, and owns one shared riser height (7.5 inches by default). Any selected section can be divided into two or three equal sections without changing the owning Level Down or its riser. Multiple Level Down objects can coexist, and their operations intentionally do not regenerate or move Railing posts.

Each Level Down now closes a selectable lowered region against the Deck Boundary, whether the polyline lies inside or outside the main footprint. Lower regions receive progressively darker shading based on their accumulated drop from the main deck. Their Dimensions-layer annotation shows only a down arrow and inches; it can be dragged freely and gains a live leader arrow back to its owning region. Selecting that annotation exposes 90-degree cleanup, side flipping, Picture Frame, Fascia, exact step drop, visibility, and deletion actions. Nested regions accumulate their step drops while Railing remains independent.

## Run the workspace

Use `npm start`, then open `http://localhost:4173`. The workspace stores the active project locally in the browser and can export a portable `.cme.json` project file.

## Repository philosophy

- Model construction concepts explicitly rather than encoding them in UI behavior.
- Keep project data and calculation results structured and serializable.
- Place shared domain services in `src/core/`.
- Build each intelligent construction object as an isolated module in `src/tools/`.
- Keep rendering, interface, commands, and history separate from domain logic.
- Validate every tool against the official projects in `examples/`.
- Record durable engineering decisions in `docs/`.
- Treat Product Lab specifications in `specs/` as authoritative and read-only unless a change is explicitly requested.
- Promote experiments from `playground/` only through intentional review.

## Relationship with DCR Sales Hub

CME is developed as a completely independent application. It may eventually replace Step 1 (Sketch) in DCR Sales Hub, but it must not depend at runtime on Sales Hub routes, global styles, project state, or internal services. Integration will be designed later through explicit, versioned boundaries.

The `railing-prototype` project is reference material only and is never modified from this repository.

Future promotion into DCR Framing Portal must follow the durable handoff at [`docs/integrations/CME-DCR-Portal-Handoff.md`](docs/integrations/CME-DCR-Portal-Handoff.md). It records the reviewed Portal baseline, local CME deltas, files to compare, acceptance checks, and the source/destination commit log so Claude or another engineer can integrate behavior without copying Portal-specific dependencies back into CME.

## Development workflow

1. Start from an approved Product Lab specification.
2. Clarify the construction object, its data contract, invariants, and validation scenarios.
3. Record important architectural choices in `docs/decisions/`.
4. Implement shared capabilities in `src/core/` and object-specific behavior in one `src/tools/` module.
5. Add automated tests in `tests/` or beside the source module.
6. Validate behavior with the relevant official projects in `examples/`.
7. Update technical documentation and the changelog before review.

## Tool approval workflow

A construction tool enters production only after:

1. Product Lab defines or approves its specification.
2. Engineering documents its model, boundaries, and construction rules.
3. Automated tests cover its data and behavior.
4. The official example projects validate expected scenarios.
5. Product and engineering review approve promotion from experimental to production code.

Unapproved ideas remain isolated in `playground/`.

## High-level roadmap

1. Establish the repository and architectural foundation. *(Complete)*
2. Define and implement Deck Boundary. *(Initial production version complete)*
3. Validate and refine Deck Boundary with Product Lab examples.
4. Add the next approved intelligent construction object listed in `src/tools/`.
5. Expand geometry, validation, serialization, rendering, command, and history services.
6. Validate increasingly complex deck projects through the official example suite.
7. Define a stable integration boundary for future use by DCR Sales Hub.

### Boundary Arch line (2026-08-31)

Select a Deck Boundary edge → **Arch line**, drag perpendicular to bend, and release to commit. Selected curves show radius and chord-to-arc midpoint height; the former C center-offset dimension is intentionally omitted. **Straighten** restores the original edge. A selected arc can become a **Curved rim joist** that follows the Deck Boundary's dominant Joist Field profile, receives joists, and uses analytical arc length in Takeoff. ### Stair framing visibility (2026-08-31)

Pictureframe stairs retain the two side stringers and fix an internal support axis 6.5 inches from each stair edge. The space between those supports is subdivided evenly at no more than 12 inches O.C.; Square cut keeps the uniform layout. Drawing and takeoff share explicit `stringerOffsetsInches`. Pictureframe also adds a full-width 2×8 PT lower-riser closure opposite the top ledger and one full-width 2×4 PT bottom tie / sole plate. The closure appears in Framing; the plate below it is counted separately in takeoff and object properties. Each is purchased in the smallest fitting commercial length, with REVIEW for overlength rather than assumed splices. These are user-requested DCR estimating rules, not approval of anchorage or load capacity.

Stairs now show plan-view framing whenever **Visibility → Framing** is enabled: a red ledger/header at the deck opening and yellow continuous side/internal stringers, using the existing framing palette. `src/tools/stair-framing/stair-framing-geometry.js` projects the same stringer count and maximum 12-inch spacing used by the stair framing takeoff onto the stair anchors. This applies to both covering types and creation previews, independently of the deck Joists switch. Display-only lines do not intercept selection, create snap targets, or add material quantities. This schematic is not a structural approval or a stringer fabrication detail.

### Stair covering types (2026-08-31)

Stair fill now shows subtle board joints matching its covering type. Square cut displays two straight boards per tread; Pictureframe displays an inner board and U frame with 45-degree front miters. Patterns start at each nosing, preserve existing colors and follow Decking visibility without changing Takeoff.

Riser fascia purchases now select 12/16 ft commercial stock independently of side fascia. Four 3 ft risers remain 12 LF net and buy one 16 ft board with reserve, instead of two 12 ft boards. Riser rows are grouped by stock length; they never include lateral cuts or the 16-inch side allowance.

Stair Object Options now selects Pictureframe or Square cut covering. New stairs default to 11-inch treads; existing depths are preserved. The isolated `src/tools/stairs/stair-covering.js` recipe derives square-shoulder tread decking, riser fascia, and side fascia with a 16-inch cut allowance per side. Geometry, Framing, and Takeoff remain synchronized through the existing dimension editor. See [formulas, migration notes, and limitations](changelog/2026-08-31-stair-covering-types.md).
